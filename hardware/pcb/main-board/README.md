GRIDNET — Main Board KiCad Schematic
REV 0.8 (matches hardware/bom.md's Board 2 — Main Board bill of materials)

What this is
------------

A KiCad 9 schematic (`main-board.kicad_sch`) for the Main Board, covering
the full circuit from hardware/bom.md's "Board 2" line items: USB-C power
input, Li-ion charge/boost/regulation, the GD32VF103CCT6 MCU with clock/
reset/boot/SWD, SPI flash + SRAM + microSD + RTC, the ESP32-C3-MINI-1U
wireless module, and the off-board connectors for the display, keyboard
controller, keyboard backlight, and speaker. There is no antenna path on
this board and no RF net — see "The antenna path never touched the board".

Alongside it, `main-board.kicad_pcb` has every part placed within the
100x80mm board outline from hardware/bom.md, **fully routed** on 2
layers (F.Cu/B.Cu) with sized power traces, and **poured with ground on
both layers**. `kicad-cli pcb drc` comes back completely clean: 0
violations of any severity, 0 unconnected items.

REV 0.8 continues the pre-fab review with two findings that the REV 0.7
pass created the conditions to see, both about things the board *claimed*
to have and did not:

1. **The antenna path never touched the board.** A phantom U.FL connector
   (`J7`) duplicating one the module already carries, a fictional `/ANT_RF`
   trace to the SMA, and an invented `ANT` symbol pin behind both. All
   three are gone, and with them the RF layout gap that headed "What's not
   done yet". See "The antenna path never touched the board".
2. **The "grid of stitching vias" was one column of nine**, because
   `BOX2I.Inflate()` mutates in place. The pours were tied together only
   down the left edge: the worst-case point on the board was 55mm from the
   nearest GND via. Now 16.8mm. See "The stitching grid was one column of
   nine vias".

REV 0.7 was the pre-fabrication design-review pass over the routed board.
Four things came out of it, in rough order of how badly they would have
bitten:

1. A **reference-designator drift bug** that had silently moved a dozen
   components into each other's board positions — including the 8MHz
   crystal's load capacitors, which ended up 51mm and 34mm away from the
   crystal. See "Reference-designator drift" below.
2. The **IP5306's switching loop spread across the whole board** — the
   boost inductor sat 63mm from the IC. See "The IP5306 switching loop".
3. **Every trace on the board was 0.2mm**, including the boost path
   rated for 2.4A. See "Trace widths".
4. **No ground plane** — every ground connection was an ordinary routed
   trace. See "Ground pours".

A fifth finding is about the tooling rather than the board: Freerouting
reports success while silently dropping connections, so the flow now
verifies with DRC and repairs what is missing. See "Routing".

An earlier revision also regenerated this PCB after it had been routed
against a *wrong* netlist: the datasheet verification pass described
below fixed real pin-numbering bugs in three of the four custom parts,
which changed which schematic pin number carries which signal for the
MCU, the ESP32-C3 module, and the IP5306, so the old copper was not just
stale but actually wrong (see "Datasheet verification results").

Neither file is hand-drawn in the KiCad GUI: both are generated by the
Python scripts in `kicad_gen/` — the schematic places components at grid
coordinates and wires them via net-label stubs (the standard label-based
wiring pattern for busy schematics, rather than long point-to-point wires
across the sheet); the PCB script places real footprints using each
part's actual courtyard geometry (measured via `pcbnew`, not guessed) so
placement is collision-free from the start. `kicad_gen/route.sh` drives
the whole sequence end to end; see "Regenerating / validating" below.

The antenna path never touched the board
-----------------------------------------

"What's not done yet" used to open with RF layout: `/ANT_RF` ran from `U9`
to a U.FL pad (`J7`) and on to the edge-mount SMA (`J8`) at whatever width
Freerouting chose, and wanted a coplanar-waveguide geometry computed for
this stackup. Working out that geometry was the plan for this pass. The
first thing that turns up on opening the board is that **`/ANT_RF` has no
`U9` pad on it at all** — the net is two connectors wired to each other,
and nothing drives it.

The ESP32-C3-MINI-1U does not bring its radio out to a castellated pad.
Datasheet v2.2 Table 3-1 lists all 53 pads: pins 1, 2, 11, 14 and 36–53
are GND, and the rest are `3V3`, `EN` and IO. There is no ANT and no RF
pad anywhere in the list. The radio leaves the module through the antenna
jack **mounted on the module itself** — that is what the "U" in `-1U`
means. So:

- `kicad_gen/build_library.py`'s symbol had a pin whose *number* was the
  string `"ANT"`, matching no pad in the footprint. That is why the
  netlist quietly produced a two-connector net instead of an error: KiCad
  ties schematic pins to footprint pads by pin number, and a pin number
  that matches nothing simply contributes nothing.
- `J7` was a second, board-mounted U.FL duplicating the module's own. The
  schematic comment beside it said as much — "U.FL pad on the
  ESP32-C3-MINI-1U module itself" — but it was placed on the PCB as a real
  footprint at (80, 35.53) anyway.
- The trace from `J7` to `J8` was therefore 19mm of copper (three
  segments, 0.2mm wide) between two connectors and nothing else, which is
  what an RF review would have been asked to impedance-match.

Worse, an edge-mount SMA soldered to the board cannot be reached by a
pigtail in the first place: its centre pin *is* a board pad. hardware/bom.md
line items 13 and 14 described exactly that — an SMA connector plus a
"U.FL-to-SMA pigtail" to connect the module to it — which cannot be
assembled as written.

**And the pigtail was the wrong connector generation.** Datasheet section
10.2 specifies the module's jack as the *third generation* connector,
compatible with Hirose **W.FL**, I-PEX **MHF III** and Amphenol **AMC**,
with a body of 2.05 x 1.7 x 1.40mm (Figure 10-3). U.FL / MHF I is the
first generation and about 2.6mm across. A U.FL plug does not mate with it.
Every mention of "U.FL" in this project's Board 2 documentation was wrong
about the part on the module, independently of everything above.

What the board looks like now: `J7` and `J8` are gone from the schematic,
from `PLACEMENT` in `build_pcb.py` and from the PCB; the `ANT` pin is gone
from the symbol; `/ANT_RF` is gone as a net. The antenna is a cable
assembly and a case feature, not copper — an MHF III/W.FL plug-to-SMA-jack
pigtail from the module's own connector to a bulkhead SMA in the enclosure
wall, with the antenna screwing onto that. hardware/bom.md REV 0.6 carries
all three as Board 2 items 13–15, with the connector and pigtail marked as
enclosure/cable parts rather than parts that get placed on this PCB — and
with the antenna itself, which REV 0.5 never listed at all.

This removes the largest item from "What's not done yet" rather than
solving it: there is no controlled-impedance net on this board, no antenna
keepout to observe (datasheet Figure 3-1 Note A: the keepout zone applies
to the PCB-antenna `-1` variant, "the latter has no antenna keepout zone"),
and no RF corridor for via placement to respect. The antenna requirements
move to the cable and the case: 2.4GHz, 50Ω, and **maximum gain 2.33 dBi**,
which is the gain of the antenna Espressif certified the module with —
exceed it and the module's existing test reports no longer cover the
product (datasheet section 10.2).

The stitching grid was one column of nine vias
------------------------------------------------

"Ground pours" below describes a 5mm grid of stitching vias placed
"wherever one fits clear of every courtyard, pad and trace". Counting them
on the finished board: **nine, all at x = 1.1mm, running down the left edge
from y = 1.1 to y = 41.1**, then stopping. Nothing else on the board.

The cause is one line of `add_stitching_vias`:

```python
if any(bb.Inflate(clear).Contains(pt) for bb in courtyards):
```

`BOX2I.Inflate()` is not a pure function. It grows the box **in place** and
returns *itself*, so every candidate point that reached a given box grew
that box by another 0.6mm before testing it. `any()` short-circuits, so
the boxes early in the list grew fastest, and after a few dozen candidates
the first courtyards it tests cover the entire board and reject everything.
The scan walks x-then-y, which is why the survivors are one partial column
at the start of the walk.

Nothing downstream could catch this. DRC does not know how many vias were
*meant* to be there, and a board with too few stitching vias is
electrically legal — just a two-layer board whose return plane is tied to
its other half only along one edge. The pour that a signal on the right
side of the board returns through had to reach the left edge to change
layers.

The fix inflates each box once, up front, outside the candidate loop:

```python
keepouts = [box for _ref, box in courtyard_boxes(board)]
keepouts += [pad.GetBoundingBox() for fp in board.GetFootprints() for pad in fp.Pads()]
for box in keepouts:
    box.Inflate(clear)
```

| | before | after |
|---|---|---|
| GND vias on the board | 22 | 180 |
| of those, on the stitch grid | 9 | 167 |
| worst-case distance from any board point to a GND via | 55.1mm | 16.8mm |

Verified after the fact, since the whole point is that DRC cannot see it:
no stitching via lands inside any footprint's courtyard, and DRC stays at
0 violations / 0 unconnected with 158 more vias on the board.

The remaining 16.8mm worst case is at (18, 58), under the display and
keyboard-controller headers' courtyards, where the grid legitimately has
nowhere to put one. The usual rule of thumb is to stitch at λ/20 for the
fastest edge present. This board's fastest are the SPI buses and USB
full-speed; a 2ns edge puts the knee at 0.5/t_r = 250MHz, and at
v_p = c/√4.3 = 1.45e8 m/s in FR-4 that is λ = 579mm, so λ/20 = 29mm.
16.8mm is inside that. 55.1mm was not. Tightening `STITCH_PITCH` below
5mm would not improve the worst case, which is set by the headers'
footprints, not by the pitch.

Reference-designator drift
---------------------------

The worst finding of this pass, and the one that explains why the other
placement problems went unnoticed: **the schematic and the PCB disagreed
about which component each reference designator named**, and nothing
checked.

`build_schematic.py` used to auto-number reference designators by the
order in which parts were placed in the file, while `build_pcb.py`'s
`PLACEMENT` dict is keyed by reference designator. Adding the IP5306's
inductor and snubber (commit 615f5d2) inserted one resistor and two
capacitors into the middle of the power tree, which renumbered every
later R and C by +1 — and `PLACEMENT` was left with the old numbering,
plus three new entries (`R14`, `C4`, `C5`) for names that were already
taken. No error, no warning: the board simply built with a dozen parts
in each other's positions.

Measured on the board as committed before this pass:

| Part | What it actually is | Where it was placed | Distance from where it belongs |
|---|---|---|---|
| `C3`, `C4` | the 8MHz crystal's 20pF load caps | by the audio amp, and in open board below the MCU | **51mm** and **34mm** from `Y1` |
| `C1`, `C2` | the IP5306's 22uF snubber and VOUT caps | flanking the crystal | **51mm** and **54mm** from `U2` |
| `R14`, `C5` | the audio PWM filter's R and C | in open board below the MCU | **61mm** and **70mm** from `U10` |
| `R9`, `R11` | BOOT1 pull-down, I2C SDA pull-up | in the RTC and ESP32 clusters | ~30mm from the pins they strap |

Crystal load capacitors 34–51mm from their crystal do not work: the
oscillator sees the trace, not the capacitor. This was a dead board, and
it looked fine.

Fixed on both sides of the door:

- `build_schematic.py` now passes an explicit `ref=` for all 48
  components, and `schematic.py`'s `place()` refuses to place anything
  without one. Refdes is now a declaration, not a side effect of file
  order. (`#PWR`/`#FLG` virtual symbols stay auto-numbered — they never
  reach the netlist's component list.)
- `PLACEMENT` entries carry the component's expected value (`"20pF"`,
  `"IP5306"`, …), and `build_pcb.py` checks every one against the
  netlist before placing anything. If the two files ever disagree again,
  the build stops and names the parts instead of quietly producing a
  wrong board.
- `build_pcb.py` also now fails on any courtyard overlap and on
  `PLACEMENT` entries for parts that are not in the netlist.

The IP5306 switching loop
--------------------------

Independent of the drift above: even under the *intended* refdes
mapping, the inductor commit put `L1`, the RC snubber and the VOUT
decoupling cap in the open band below the MCU (y=62–68mm) rather than
next to the IP5306 at (11.5, 5.8). Its stated reason — that the CR2032
holder's real 27x24mm courtyard fills the power-tree column from y=50
down — is true but solved the wrong problem: the parts did not need to
be in that column, they needed to be next to the IC.

A 1uH boost inductor 63mm from its switching node is not a boost
converter. The `SW` node loop area and its parasitic inductance are set
by exactly that distance, and everything the snubber exists to damp gets
worse with it.

Re-placed tight around `U2`, whose BAT/SW/VOUT pins (6/7/8) are all on
its right-hand side:

- `L1` immediately to its right, ~1mm courtyard gap
- `C5` (VOUT decoupling), `R14` + `C4` (the SW-node snubber) on the row
  just below

`SW1` (the PWR_KEY button) moved out to the MCU column to make room. It
is a momentary switch on a static input, so distance costs it nothing —
which is exactly what made it the right thing to displace.

Trace widths
-------------

Every net on this board was routed at the 0.2mm default, including the
IP5306 boost path — flagged for review when the inductor was added, and
fixed here. Netclasses live in `main-board.kicad_pro`, written by
`build_pcb.py`'s `NETCLASSES` table (KiCad 7+ keeps netclasses in the
project file, not the board), so the widths are in place *before* the
board goes to the autorouter rather than being retrofitted onto finished
copper.

Sizing is IPC-2221's external-layer curve at 1oz copper and a 10°C rise:
0.2mm carries 0.74A, 0.4mm 1.23A, 0.8mm 2.03A.

| Class | Nets | Width | Why |
|---|---|---|---|
| `Power_Batt` | `/VBATT`, `/IP5306_SW` | 0.8mm | The board draws 355mA at 5V (docs/firmware-arch.md REV 0.6), ~545mA battery-side, ~0.7A peak with boost ripple, plus the MCP73831's 450mA charge current on the same net. Sized towards the IP5306's own 2.4A rating instead: 0.8mm carries 2.03A at 10°C and the full 2.4A at roughly 15°C |
| `Power_5V` | `+5V`, `VBUS` | 0.4mm | 355mA system plus the PAM8403's ~500mA peak into 1W/8Ω ≈ 0.9A design maximum |
| (default) | `GND`, `/+3V3_MCU`, `/+3V3_RF`, signals | 0.2mm | see below |

**Why the battery class is not 1.0mm** (the exact 2.4A/10°C width): `U2`
is an SOP-8 whose pads are only 0.60mm across the trace direction. A
1.0mm trace would have to neck down at both ends of the shortest and
most critical segment on the net. At 0.8mm, Freerouting necks to 0.601mm
for the last 1.4mm into the pad and runs full width everywhere else,
which is the right answer.

**Why GND and the 3V3 rails deliberately have no class.** GND's current
is carried by the pours, not the traces. `+3V3_MCU` carries ~150mA and
`+3V3_RF` peaks near 350mA on ESP32-C3 transmit — both well inside
0.2mm's 0.74A. A first cut of the table gave all three 0.4mm "for
margin" and **Freerouting could not route any of them**: `U5` is an
LQFP-48 on a 0.5mm pitch, and a 0.4mm trace leaving a 0.3mm pad there
comes within 0.15mm of the neighbouring pad, under the 0.2mm clearance
rule. The MCU's own GND and 3V3 pins were the failures both times.
Wider is not automatically safer — it has to fit the escape geometry at
both ends.

Ground pours
-------------

The board had no ground plane at all: every ground connection was an
ordinary routed trace. Both copper layers now carry a GND zone inset
0.5mm from the outline (`add_gnd_zones` in `build_pcb.py`), filling
6270mm² on F.Cu and 6727mm² on B.Cu.

- **Solid pad connections, not thermal reliefs.** Thermal spokes were
  tried first and left 11 pads "starved" — fewer than the two spokes
  KiCad requires, because a 0603 pad with a trace already attached has
  no perimeter left for a second one. Solid copper costs some
  hand-soldering convenience on ground pins and buys a lower-impedance
  return everywhere; this board is reflow-assembled, so that is the
  right trade.
- **Island removal on.** Copper that ends up connected to nothing is
  dropped rather than left floating for DRC to report.
- **Zone clearance matches the board rule (0.2mm) rather than exceeding
  it**, so the pour can reach between fine-pitch escape traces instead
  of stopping short and stranding copper.
- **Vias**: the 3x3 array under `U9`'s thermal pad (pin 49), which is
  what Espressif's hardware design guidelines actually ask for, plus a
  5mm grid of stitching vias (`STITCH_PITCH`) wherever one fits clear of
  every courtyard, pad and trace — 167 of them. Earlier revisions of this
  file said "9mm grid", which matched neither the constant nor the board:
  what was actually placed was nine vias in a single column, and only the
  count made that visible. See "The stitching grid was one column of nine
  vias".

Two ordering constraints, both learned the hard way:

- **Thermal vias go in at placement time, before routing.** Given the
  space, Freerouting will run B.Cu traces straight under the module;
  vias added afterwards land on top of them (`/AUDIO_SHDN` and
  `/KBL_DRAIN` were both shorted this way).
- **The pours go in after routing, not before.** Zones present at
  DSN-export time become Specctra planes, and the router then treats GND
  as already connected and lays no GND copper at all — which leaves every
  ground connection depending on the pour reaching that exact pad. On a
  dense two-layer board it does not: routing chops the F.Cu pour into
  islands, and DRC found 16 GND fragments and pads stranded that way.
  Routing GND as ordinary traces first and pouring on top gives
  connectivity the router can guarantee, with the pour's lower impedance
  and thermal path on top of it rather than instead of it.

What the pour does *not* yet include: a deliberate return-path review of
the SPI/I2C buses, and any thermal-relief exception for hand-rework.

Datasheet verification results
-------------------------------

Each part's real pinout was pulled from its primary-source datasheet (not
a summary site) and compared pin-by-pin against what the generated
symbol had. Three of the four were substantially wrong:

- **GD32VF103CCT6.** Pins 1-13 were already correct. From pin 14 on,
  the symbol had inserted `VSS_1`/`VDD_1` two positions early, shifting
  every following pin by +2 (and a second such insertion at pins 37-38
  shifted the rest further) — the net effect: 35 of 48 pins named the
  wrong signal. The *real* pinout, once correctly transcribed, matches
  the well-known STM32F103C8/CB LQFP48 numbering exactly (the mirroring
  claim in the old description was directionally right; the symbol just
  didn't implement it correctly pin-for-pin). Fixed in
  `kicad_gen/build_library.py`.
- **ESP32-C3-MINI-1U.** The module has 53 physical pads (mostly GND and
  NC around the perimeter); the symbol had instead numbered its 19
  functional signal pins sequentially 1-19, which matches almost none of
  them. For example the old symbol's pin 8 ("IO4") is the real module's
  `EN` pin; the old pin 17 ("U0RXD") is a real `NC` pad. Every pin was
  re-numbered against Table 3-1 of Espressif's datasheet. The footprint
  was still the WROOM-02U placeholder at this point — fixed separately,
  see "Real ESP32-C3-MINI-1U footprint" below.
- **IP5306.** All 8 numbered pins were wrong, and the symbol was missing
  two of the part's real pins outright: `LED3` (pin 4) and `SW` (pin 7,
  the DCDC switch node). It had also invented two `GND` pins (old 3 and
  6) that don't exist — the real IP5306 only has one ground reference,
  the exposed PowerPAD, which is now modeled as pin 9. Fixing this
  surfaced a real design gap, not just a labeling one: **no inductor
  existed anywhere in this design**, and without one on `SW` the boost
  path (`BAT` -> `VOUT`) can't function. This has since been fixed — see
  "IP5306 boost inductor" below.
- **23LC1024.** Checked as a control/sanity case — it was already
  correct, all 8 pins matched Microchip's datasheet exactly.

**Regenerating the PCB against this fix.** Done in a follow-up pass: netlist
re-exported, `build_pcb.py` re-run (placement is driven by reference
designator + footprint, so component *positions* didn't move, but every
pad's *net assignment* on the MCU, the ESP32-C3 module, and the IP5306
came from the corrected netlist this time), then re-routed from scratch
— the old copper was routed against the old netlist and couldn't just be
relabeled in place. See "Routing" below for how that pass went.

IP5306 boost inductor
----------------------

Fixed as a follow-up to the pin-numbering bug above. The IP5306
datasheet's own "Typical Application Schematic" (Figure 7) shows the
boost/charge inductor bridging `SW` (pin 7) directly to `BAT` (pin 6) —
**not** to `VOUT` as an earlier read of this design guessed; the
`SW`-`BAT` inductor is shared between the buck charger and the boost
discharger, and `VOUT` (pin 8) is a separate internally-switched output.
Added per that reference circuit:

- **L1, 1uH** (`Inductor_SMD:L_6.3x6.3_H3` — a generic shielded power
  inductor footprint, not a specific vendor part; the datasheet doesn't
  specify one either) between `SW` and `BAT`/`/VBATT`.
- **R14 (0.5R) + C4 (22uF) in series**, from the `SW`/`L1` junction to
  GND — the datasheet's `R4`/`C2`, a small RC snubber damping switching
  ringing on the `SW` node. This carries only transient ringing current,
  not the inductor's main current, so a standard 0603/0805 pair is fine
  even though the inductor itself is a boost-converter-current part.
- **C5, 22uF** at `VOUT`/`+5V`, directly at the IC — the datasheet's
  figure uses a 4x22uF bank there; simplified to one cap here, the same
  simplification style already used for the mono audio path elsewhere in
  this design.

All three were new components when the inductor was added, and were
first placed in the open board area below the MCU cluster rather than in
the power-tree column, on the grounds that the CR2032 holder's courtyard
fills that column from y=50 down. That reasoning is what "The IP5306
switching loop" above unpicks: it put a boost converter's switching loop
63mm across the board. They now sit tight around `U2` — see that section
for the current positions.

Real ESP32-C3-MINI-1U footprint
--------------------------------

Fixed as a follow-up to the datasheet verification pass above, which
fixed the schematic symbol's pin *numbers* but left the PCB footprint as
the same-family `RF_Module:ESP32-C3-WROOM-02U` placeholder (a different,
smaller module standing in for placement purposes only — see the old
confidence table entry). Replaced with the real thing rather than
hand-transcribing dimensions off the datasheet's land-pattern drawing
(error-prone for a 53-pad castellated footprint, and exactly the kind of
mistake this whole verification pass exists to catch): Espressif
publishes an official KiCad library at
[espressif/kicad-libraries](https://github.com/espressif/kicad-libraries)
(CC-BY-SA 4.0, the same license terms as KiCad's own official libraries),
and its `ESP32-C3-MINI-1U.kicad_mod` is vendored unmodified into
`gridnet_footprints.pretty/` — see that directory's README.md for exact
provenance. `kicad_gen/build_pcb.py` gained a small `LOCAL_FOOTPRINT_LIBS`
lookup so it can load project-local footprints alongside the ones it
already pulls from KiCad's bundled libraries.

Verified before use (not just trusted because it's "official"): 53
distinct pad numbers, with pad 49 (`GND`) present as the expected 3x3
array of thermal-pad via pads under the module — matches Table 3-1 of

Design assumptions (things this schematic decided that the BOM/docs didn't
spell out)
------------------------------------------------------------------------

- **DS3231M substituted for the BOM's DS3231SN.** Same SCL/SDA/VBAT/
  32KHZ/INT-SQW functionality; DS3231M is the version KiCad ships a real,
  verified symbol for. If REV 0.6 of the BOM should specifically source a
  DS3231SN, the footprint/ordering part number differs but the schematic
  pinout is unaffected (compatible pin function set).
- **USB D+/D- routed to the ESP32-C3's native USB (IO18/IO19), not the
  MCU.** The GD32VF103 has no native USB peripheral, so DFU-over-USB (per
  docs/firmware-arch.md) has to come through the ESP32-C3 module instead.
  This is a design assumption, not a documented requirement — confirm it
  matches the intended firmware update path before relying on it.
- **IP5306 VIN left unconnected; MCP73831 handles charging instead.**
  IP5306 is a combined boost + charge-management IC, but this design uses
  it only for its 5V boost path (BAT -> VOUT) and handles Li-ion charging
  separately with a dedicated MCP73831. IP5306's own charge-input pin
  (VIN) is marked `no_connect` rather than wired to VBUS, to avoid two
  charge controllers fighting over the same battery. The boost path
  itself runs through `L1`, a 1uH inductor on `SW` shared with the
  charger — see "IP5306 boost inductor" above.
- **Mono audio.** PAM8403D is a stereo amplifier, but hardware/bom.md
  specs one 1W/8Ω speaker. INL, INR, and VREF are all tied to the same
  filtered PWM node, and only the left channel output (LOUT+/LOUT-) is
  wired to the speaker connector; the right channel is `no_connect`.
- **CC1/CC2 strapped 5.1k to GND.** Fixed "UFP sink" strapping so any
  USB-C charger or host offers 5V — this board doesn't negotiate USB-PD.
- **BOOT0 has both a pull-down (default: boot from Flash) and a 2-pin
  override jumper** to force it high for factory/recovery reflashing
  without needing a bodge wire.

Net plan (high level)
----------------------

- **Power:** VBUS (from USB-C) -> MCP73831 -> VBATT (battery) -> IP5306
  boost -> +5V -> two AMS1117-3.3 rails: +3V3_MCU (MCU + all digital
  logic) and +3V3_RF (ESP32-C3 module, kept separate for RF supply
  cleanliness).
- **MCU (GD32VF103CCT6):** 8MHz crystal on OSC_IN/OSC_OUT, NRST with pull-up
  + reset button, BOOT0 pull-down + override jumper, BOOT1 pull-down, SWD
  header (SWDIO/SWCLK/+3V3_MCU/GND).
- **SPI1** (SCK/MISO/MOSI shared bus): W25Q64JVSSIQ flash (FLASH_CS),
  23LC1024 SRAM (SRAM_CS), microSD (SD_CS).
- **I2C1:** DS3231M RTC (SCL/SDA, 4.7k pull-ups each), with its own CR2032
  holder on VBAT_RTC (externally-sourced net, PWR_FLAG'd — see below).
- **USART1:** MCU <-> ESP32-C3-MINI-1U (cross-connected TX/RX).
- **SPI2:** MCU <-> RA8875 display module header (SCK/MISO/MOSI/CS/RESET/
  INT).
- **USART2:** MCU <-> CH552G keyboard-controller header.
- **PWM outputs:** KBD_BACKLIGHT_PWM (via 2N7002 low-side switch, drives
  external LED array) and AUDIO_PWM (via an RC filter into PAM8403D's
  audio input).
- Every otherwise-unused MCU/ESP32/RTC/microSD/amplifier pin is explicitly
  marked `no_connect` (not left dangling) — see the bottom of
  `kicad_gen/build_schematic.py` for the full list and why each one is
  unused.

--------------------------

not hand-edited. To rebuild from scratch:

```
cd hardware/pcb/main-board/kicad_gen
```

```
kicad-cli sch export svg main-board.kicad_sch -o /tmp/render/
```

Current ERC result (after the datasheet-verification pin fixes, the
IP5306 inductor addition, the real ESP32-C3-MINI-1U footprint, and
grounding its remaining GND pads above, and removing the antenna
connectors): **368 violations, 0 errors.**
All remaining warnings are benign / expected in a headless-generated
schematic without a full project sym-lib-table registered:

- `endpoint_off_grid` (353) — cosmetic, wire/pin endpoints not snapped to
  KiCad's visual grid
- `lib_symbol_issues` (10) — artifact of validating without this
  environment's full symbol-library table registered
- `pin_to_pin` (4) — intentional: each SPI flash/SRAM's `~WP`/`~HOLD` pins
  are tied directly to its own VCC pin (both real, both correct — not a

- `footprint_link_issues` (1) — same cause as `lib_symbol_issues`: this
  headless environment doesn't have `gridnet_footprints` registered as a
  project footprint library, so ERC can't confirm the link; the footprint
  itself loads and places fine (see "Real ESP32-C3-MINI-1U footprint"
  above and the DRC result below)

The PCB is a five-stage pipeline, all of it driven by
`kicad_gen/route.sh`:

```
cd hardware/pcb/main-board/kicad_gen
FREEROUTING_JAR=/path/to/freerouting.jar JAVA=/path/to/java-25 ./route.sh
```

which runs, in this order and for the reasons given in "Ground pours"
and "Routing":

1. `build_library.py` + `build_schematic.py` — symbols and schematic
2. `kicad-cli sch export netlist` — the netlist `build_pcb.py` reads
3. `build_pcb.py` — placement, `U9`'s thermal vias, and the netclasses
   written into `main-board.kicad_pro`
4. Specctra DSN out → Freerouting → SES back in, then
   `finish_routing.py` to verify and repair
5. `build_pcb.py --pour` — GND zones, stitching vias, fill

then runs DRC and fails if anything is an error or unconnected. If the
repair step cannot close a gap it throws that routing away and runs
Freerouting again (up to `ATTEMPTS`, default 3) rather than leaving a
hand-patched board that the next regeneration would lose.

Any stage can also be run on its own; they are ordinary scripts.

Current DRC result (routed and poured board): **0 violations, 0
unconnected items** — clean at every severity, including the
`drill_out_of_range` warnings that dogged earlier revisions (those
traced to the WROOM-02U placeholder footprint's 0.2mm holes and went
away with the real footprint). 46 footprints, 86 nets, 806 tracks, 239
vias, both GND pours filled (F.Cu 6385mm², B.Cu 6955mm²).

REV 0.8's board is the REV 0.7 board minus `J7`, `J8` and the three
`/ANT_RF` tracks, plus 158 stitching vias and a refill. That was done as

Routing
-------

`main-board.kicad_pcb`'s copper (F.Cu/B.Cu) was routed by
[Freerouting](https://www.freerouting.app/) v2.2.4 (the standard
open-source autorouter for KiCad, run via its CLI in headless mode — no
GUI, no manual click-routing) rather than by hand or left unrouted. This
environment ships neither Freerouting nor a Java runtime new enough to
run it, so both were fetched for this pass: Freerouting's jar from its
GitHub releases, and a Temurin JDK 25 (Freerouting 2.2.4 requires
class-file version 69, i.e. Java 25 — the environment's stock JRE was
Java 21).

The exchange is the standard KiCad-\<->Freerouting workflow, all via the
`pcbnew` Python API (no GUI needed for either direction):

```
python3 -c "
import pcbnew
board = pcbnew.LoadBoard('main-board.kicad_pcb')
pcbnew.ExportSpecctraDSN(board, 'main-board.dsn')
"
java -jar freerouting.jar -de main-board.dsn -do main-board.ses \
    --gui.enabled=false -mp 10
python3 -c "
import pcbnew
board = pcbnew.LoadBoard('main-board.kicad_pcb')
pcbnew.ImportSpecctraSES(board, 'main-board.ses')
board.Save('main-board.kicad_pcb')
"
```

**Freerouting reports success while dropping connections.** This is the
tooling finding of REV 0.7, and it invalidates how earlier revisions of
this document read its output. Across a dozen runs on this board:

- It printed "Auto-router session completed … 0 unrouted" and returned a
  session file with `/USART2_RX` **entirely absent** — no wire for the
  net at all.
- It routed one of `J1`'s two D- pads and not the other, and called the
  net finished. `J1` is a reversible USB-C receptacle, so D+ and D- each
  land on two pads with the *other* signal's pad physically between them
  on a 0.5mm pitch; whichever pair gets routed first takes the corridor.
- Which connections it drops **varies between identical runs**. Two runs
  on the same input dropped different nets.

The response is `kicad_gen/finish_routing.py`: after importing the
session, ask KiCad's DRC what is actually unconnected and route it.
Repair is a deterministic grid maze router (A* on a 0.05mm grid, both
copper layers, Manhattan heuristic, vias costed at 12 cells so it does
not stitch gratuitously), with rip-up-and-reroute as a fallback for
connections that cannot be finished around what the autorouter already
committed to. Anything it cannot close makes `route.sh` throw that
routing away and run the autorouter again.

The repair step earns its keep — in successive runs of this pass it
closed `/USB_DN`'s stranded pad, `/BOOT0`, `/SRAM_CS` and `/USART2_RX`,
none of which the autorouter admitted to leaving open.

Things that were tried and do not work, recorded so they are not tried
again:

- **Pre-routing the awkward connections so Freerouting has to work
  around them.** Reasonable in principle and standard practice by hand;
  in practice Freerouting v2.2.4 either hangs for over nine minutes or
  dies with a `NullPointerException` in its own
  `PolylineTrace.normalize`, reliably, whenever the pre-existing wiring
  lands on `J1`'s 0.5mm-pitch pads. Repair after the fact is the only
  order that works.
- **Re-running the autorouter on the partly-routed board** to let it
  finish what it missed. It reports the missing connections as unrouted
  and still cannot place them: by then `U5` pad 40 sits in a 2 x 5.6mm
  pocket of F.Cu with no via site anywhere in it. It routed itself into
  a corner and then said it was done.

Two details of the repair router worth keeping, because both were bugs
first:

- The grid is 0.05mm, not 0.1mm. `J1`'s pad rows sit on a 0.5mm pitch
  with centres at x.x5 coordinates, so a 0.1mm grid cannot land on a pad
  centre at all — and the escape lane between two neighbouring pads is
  exactly 0.45mm, exactly the clearance a 0.2mm trace needs. Half a grid
  cell of rounding closes it.
- Pads are modelled as rectangles. An earlier version used a stadium
  (a segment grown by the pad's short half-dimension), which tucks
  inside a rectangle's corners: a via placed diagonally off a 0603 pad
  passed the check and then failed DRC by 0.03mm.

**A note on trusting the previous `/USB_DN` write-up.** Earlier
revisions of this file described finishing `/USB_DN` by hand with three
F.Cu segments jogging east around the connector, and concluded the west
corridor was full. That analysis was sound for the placement it was
made against, but the placement has since changed — see "USB-C fan-out"
below.

**USB-C fan-out.** `R1` and `R2` (the CC pull-downs) used to sit at
y=30.6, directly east of `J1` between the D+ and D- pad rows, and
`/CC1`'s diagonal run to `R1` closed the only gap the D- pair had to
cross in. They now sit above and below the fan-out band — `R2` at y=27
near its own pad at 28.85, `R1` at y=34 near its own pad at 31.85 —
which is where they belonged anyway.

**Why `/DISP_CS` routed fine this time.** The earlier investigation
(previous PCB revision, see git history for the full writeup) spent
considerable effort diagnosing why `/DISP_CS` wouldn't route, and
concluded the real blocker was `/+3V3_MCU`'s routing elsewhere on the
board. That diagnosis turned out to be moot: the datasheet verification
pass found the MCU symbol's pin 27 was mislabeled `PB12` (the schematic's
`/DISP_CS`) when the real MCU's pin 27 is `PB14` — `PB12` is actually
pin 25. So that entire investigation was against a net that was never
really `/DISP_CS` to begin with; it was whatever the old, wrong netlist
happened to assign to pad 27. On the corrected netlist, the *real*
`/DISP_CS` (pad 25) sits in a different, apparently less congested
neighborhood and Freerouting completed it without issue.

PCB placement notes
--------------------

- **Footprint sizes, not guesses.** Every part's real courtyard geometry
  was measured via `pcbnew` (`build_pcb.py`'s courtyard-center correction,
  and the shelf-packing math behind the `PLACEMENT` dict in that file)
  before any coordinates were chosen. The first hand-placed attempt at
  laying this board out — done *before* checking real footprint sizes —
  produced 7 courtyard overlaps and several pad-to-pad net-shorting
  violations, most notably because the CR2032 holder's real footprint is
  27x24mm (not the few-mm size its schematic symbol suggests). Measure
  first, place second.
- **Footprint anchors aren't always courtyard centers.** Pin headers are
  anchored at pin 1, not the row's midpoint; the SMA edge-mount connector
  (`J8`, since removed — see "The antenna path never touched the board")
  had its body anchored well off to one side of its mounting pin.
  `build_pcb.py` places every footprint once, measures where its courtyard
  actually landed, and corrects the anchor so `PLACEMENT`'s coordinates
  consistently mean "courtyard center" regardless of the footprint's own
  quirks — a real, repeatable bug (not just a cosmetic one) found and
  fixed while placing the two on-board header rows.
- **`no matching net` is expected for `J5` and `J1`.** Each has a few
  real footprint pads (shield tabs, mechanical/detect pins) with no
  counterpart in the schematic's simpler symbol — harmless. `U9` (the
  ESP32-C3-MINI-1U) used to be in this list too, for 34 unmatched pads;
  now that every real `GND` pin is drawn and wired (see "Real
  ESP32-C3-MINI-1U footprint" above), only its 14 genuinely `NC` pads
  are unmatched, which is correct — there's nothing to wire them to.

What's not done yet
--------------------

REV 0.8 closed the item that used to head this list — RF layout around
the antenna path — by establishing that there is no RF net on this board
to lay out, and re-stitching the pours that REV 0.7 only appeared to
stitch. REV 0.7 before it closed trace widths on the boost path and the
ground pour itself. What is left:

- **Return-path continuity for the SPI/I2C buses.** The pours give every
  signal a return plane, but nothing has checked that a bus does not
  cross a slot in the pour where its return current would have to detour.
- ~~A stackup decision~~ — closed. It is now `STACKUP` in `build_pcb.py`,
  written into the board's own design rules rather than into prose: 1.6mm
  FR-4, two layers, 1oz copper, 0.2mm minimum track and clearance, 0.6mm
  vias on 0.3mm drills, 0.15mm annular ring, 0.25mm hole-to-hole.

  Writing it down turned up something worse than an undocumented
  assumption. **KiCad's minimums were left at their defaults, which are
  zero.** `m_TrackMinWidth` and `m_MinClearance` both read back as 0.0mm on
  the finished, DRC-clean board — so every "0 violations" this project has
  reported was measured against no process limit at all. A 0.05mm trace, a
  via with no annular ring, two holes touching: all would have passed.

  The values above are what the board already uses, promoted from
  convention to rule, so DRC now catches anything that drifts *below* what
  the design was drawn to. The routed board passes them unchanged: 0
  violations, 0 unconnected, same as before. That is the point — the rules
  describe this board, they do not reshape it.

  Still open, and a different question: whether these minimums suit the
  manufacturer actually chosen. They are this design's own floor, not a
  claim about anyone's process.
- **A human eye on the autorouted result before fab.** DRC-clean and
  netclass-correct is not the same as well laid out. The specific things
  a review should look at: the density of the escape fan under `U5`, and
  the 16.8mm stitching hole under the top-edge headers.
- A second schematic sheet (and PCB) for the PLC/Power Board and PLC
  Adapter (see hardware/bom.md's Board 1 and "PLC Adapter" sections) — out
  of scope for this pass, which covers Board 2 (Main Board) only.
